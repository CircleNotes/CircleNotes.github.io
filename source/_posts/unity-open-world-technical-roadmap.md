大世界技术涉及资源、表现、模拟和内容生产等多个系统。只把地图切成多个场景，或单独优化一次 Draw Call，都还不足以回答它们如何协作、何时加载与释放、以及如何在不同设备上保持稳定。

这份路线从成熟作品提出的问题出发，在 Unity 中建立小规模实验，再把验证过的部分整合成可巡游的世界样例。研究沿着“案例 → 假设 → 对照实验 → 双平台测量 → 选型复盘”推进，每项任务都保留前置依赖、行动步骤、产物与验收条件。

**阅读方式：** 先看阶段总览与里程碑，再按当前问题进入详细任务。案例资料是研究入口，任务不是已完成清单；官方确认、观察与推测会分开记录。

## 目标与范围

以当前 Unity 项目为实验载体，建立“成熟案例研究 → 方案比较 → 小规模实验 → 双平台测量 → 综合样例 → 复盘”的学习路径。最终交付可复测的 Unity 大世界技术 Demo、技术决策记录与可复用的模块边界，而不是复刻某款完整游戏。

技术栈以 Unity 为主，目标平台同时覆盖 PC 与移动端。案例从《艾尔登法环》扩展到不同世界结构与内容约束的作品，通过对比方案寻找适用边界。具体测试设备、Android/iOS 覆盖范围、性能预算与时间安排在任务 00.01 中确定，先建立依赖关系，再制定日历排期。

实验环境以 Unity **6000.3.22f1**、URP **17.3.0**、Amplify Impostors **1.0.2** 为起点，利用现有 PC/Mobile 渲染配置与插件示例逐步建立实验世界。这些版本是本次规划的环境记录，相关功能仍需按各阶段要求完成构建、运行与设备验证。

## 规划路线与取舍

1. **推荐：按技术问题推进，案例穿插。** 共用 Unity 实验世界，对流送、远景、可见性、光照等问题分别比较方案，每个里程碑验证双端。
2. **按游戏整套复刻。** 体验直观，但美术与玩法会挤占技术研究，且内部算法多未公开；只截取具有研究价值的局部场景。
3. **先建立通用框架或堆叠插件。** 易过早抽象，也可能跳过原理与测量；主线优先 Unity 现有能力和现有插件，遇到实测瓶颈后才扩展。

主要技术候选：GameObject / MonoBehaviour、URP、Additive Scene、Addressables、Mesh LOD、Amplify Impostors、Unity Terrain / Mesh 地形、AI Navigation、Unity 性能工具。Addressables 尚未安装，后续任务需验证版本再接入。HLOD、APV、GPU Resident Drawer 和 GPU 遮挡均为“需验证的候选”，不承诺全部采用。DOTS、自研 GPU 剔除、虚拟纹理等放入选做。

## 案例研究规则

- **A：原始公开资料确认。** 开发者演讲、官方技术文档、可核对的公开代码；记录日期和适用版本。
- **B：可重复观察。** 官方影像或自有实机观察，只证明可见行为与效果。
- **C：技术假设。** 根据画面或表现提出的实现解释，必须标明推测，并设计实验。
- 未取得讲稿全文时，官方简介只能证明公开讨论的议题，不能证明讲稿中的算法细节。历史博客不代表游戏当前完整架构。
- 每份研究卡包括：问题、来源、证据等级、方案、代价、替代方案、Unity 最小实验、PC/移动端差异、结论边界。
- 案例之间比较的是约束与方案；Unity 实验是借鉴实现，不能声称还原其他引擎内部。研究只使用可合法访问的资料与项目可用素材。

| 案例 | 优先研究问题 | Unity 实验方向 |
|---|---|---|
| 艾尔登法环 | 关卡数据、导航数据生成、资源依赖、内存诊断；地标和多层区域观察 | 分块元数据、导航烘焙、依赖可视化、地表/地下过渡 |
| Firewatch | 空间分组、路线与区域流送 | 距离网格、区域触发和混合调度的对照 |
| Rust | 动态世界、Impostor 提交、遮挡与环境音成本 | 密度压力测试、批次与剔除、分级模拟 |
| 地平线 | 资源管线、调度、内存、程序化局部布置与制作工具 | 预算调度、依赖分组、确定性布置、资产元数据与增量制作 |
| 旷野之息 | 探索空间、视线遮露、局部规则交互 | 灰盒路线、可控规则、卸载后的状态一致性 |

## 模块边界与共用约束

- **常驻层：** 玩家、相机、世界协调、配置、采样与状态服务。
- **世界数据：** 稳定 ChunkId、对象 ID、区域/层级、边界与资源地址；逻辑状态与场景实例分离。
- **流送层：** 计算目标驻留集合、调度和就绪；资源提供者负责加载句柄及释放，两者分离。
- **表现层：** 地形、植被、LOD/Impostor/HLOD、光照和环境；可见、不模拟、停用、卸载是不同操作。
- **模拟层：** 导航、交互、物理、动画与音效按预算分级，关键状态可跨卸载恢复。
- **工具层：** 分块编辑、派生数据生成、依赖/内存可视化、构建与回归。

PC 和移动端共用数据模型与正确性要求，分别设置视距、密度、图集、阴影、资源预算和模拟频率。任何优化都保留可比较的基线与回退路径。传统多场景遮挡数据不能按独立块自动合并；光照贴图、传统探针、APV、反射与遮挡需分别验证驻留边界，见文末官方来源。

## 流程化制作与程序化协作

大世界还需要回答内容怎样持续生产和修改：从参考、灰盒、素材制作到导入、规则布置、分块、烘焙和平台构建，哪些步骤由人编辑，哪些由规则生成，一次改动会让哪些产物失效。这里把**流程化制作**作为贯穿主线的内容生产方法；其中的**程序化生成**负责重复性工作，两者分别定义目标和验收。

### 制作链路与数据归属

| 环节 | 权威输入 | 主要产物 | 需要验证的问题 |
|---|---|---|---|
| 参考与灰盒 | 空间目标、道路、地标、平台预算 | 区域布局与内容需求 | 视线、通行与资源尺度是否合理 |
| DCC 与 Unity 导入 | 源模型、纹理、材质、导入预设 | 规范化原型资源库 | 单位、轴向、原点、UV、引用与重导入是否一致 |
| 手工与规则布置 | 原型库、种子、规则、密度图、排除范围、手工覆写 | 具备稳定 ID 的世界源数据 | 重生成是否可重复，是否保留道路与手工精修 |
| 分块与派生数据 | 世界源数据、区域边界、生成参数 | Chunk 清单、LOD/Impostor/HLOD、碰撞、导航、光照 | 是否正确计算共享与跨块依赖，过期数据能否发现 |
| 平台转换与构建 | 通过检查的内容、PC/移动端参数 | 平台资源包、版本清单、Player | 平台缓存有无混用，清单与产物是否对应 |
| 回归与内容迭代 | 固定路线、设备、检查规则、上次有效产物 | 质量/性能报告、问题与修复记录 | 修改范围、制作成本和失败恢复是否可解释 |

源素材、生成配方和手工覆写是可编辑输入；派生数据可以重建，预览结果和临时输出不应反向变成唯一权威数据。DCC 工具是可替换的输入端，主要技术栈仍是 Unity；不要求为了执行主线先购买或引入某个特定工具。

### 三种制作方式的对比

| 方式 | 主线研究内容 | 重点代价 |
|---|---|---|
| 手工制作 | 灰盒、关键地标、道路、关卡精修与流程基线 | 重复劳动、编辑冲突、修改传播与人力维护 |
| 离线程序化生成后烘焙 | 植被/装饰布置、局部地表与派生数据生成；优先在小区域验证 | 生成耗时、版本兼容、增量失效与手工覆写 |
| 运行时生成或 GPU 局部布置 | 对有明确收益的内容做独立实验；可与离线/手工内容混合 | 启动与峰值耗时、设备兼容、确定性、持久状态与调试 |

主线采用“人工确定关键布局和地标，基础规则处理重复布置，覆写层保留精修”的候选流程，再根据制作时间、画质、存储和双端成本与纯手工方案比较。它是本项目待验证的选择，不代表上述作品都采用同一条制作流程。

### 增量处理、质量检查与迭代效率

- **依赖与缓存：** 输入、规则、工具、Unity/包版本、目标平台和配置共同决定产物是否仍有效；改一个共享材质或跨块烘焙输入可能影响多个区域，不能承诺永远只重建一块。
- **可重复与可迁移：** 相同版本输入应产生可核对的逻辑布置；规则更新、对象删除与改名必须处理稳定 ID、手工覆写和历史存档。烘焙或压缩结果按明确容差检查，不默认字节完全一致。
- **失败与恢复：** 临时输出通过检查后才切换有效内容清单；失败、中断或过期缓存不能覆盖上一份完整可用产物。先完成单机批处理，再决定是否需要构建农场。
- **质量与反馈：** 自动检查格式、引用、ID、预算和过期数据，人工检查关键视线、路线、接缝与设备画面；修复应回到源数据或覆写层。
- **效率指标：** 记录编辑到预览的等待、全量/增量时间、缓存命中、重建范围、峰值内存、失败恢复时间与人工步骤数，并保留纯手工基线。

对应任务：**02.05—02.06** 提前验证制作契约和基础生成，**11.05—11.12** 完成导入、协作、增量生成、批处理、质量检查与交付闭环。阶段 11 是任务分类，所需工具随内容模块一起推进，不应等运行时全部做完才开始。

[Guerrilla 的工具规模化讲座](https://www.guerrilla-games.com/read/scaling-tools-for-millions-of-assets-for-horizon-forbidden-west)可作为资产数据库与内容工具的研究入口；[程序化布置讲座](https://www.guerrilla-games.com/read/gpu-based-procedural-placement-in-horizon-zero-dawn)连接规则编辑与运行时布置。当前依据官方简介确定研究范围，细节仍需核对原始讲稿。Unity 侧从 [Presets](https://docs.unity3d.com/6000.3/Documentation/Manual/Presets.html) 和 [AssetPostprocessor](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AssetPostprocessor.html) 等现有能力评估导入一致性与自动处理。

## 任务组织与时间口径

共 **64 项主线任务、192 个行动步骤、8 项进阶选题**。可下载[结构化任务 JSON](/downloads/unity-open-world/roadmap.json)，用于导入个人任务工具或继续拆分。每个任务包含依赖、目的、步骤、产物和验收。建议单次投入约 2 小时，表中的次数只表示初始拆分尺度，不是工期承诺；遇到设备、资料或复杂实现问题时继续拆分，不通过缩减验收伪装完成。案例只需先明确当前技术问题，后续模块无需等待全部案例读完。

P0：当前基线任务；P1：依赖满足后推进的主线；进阶选题保留在候选池。阶段号用于分类，并非必须串行的排期；工具和性能工作随对应模块推进。

|---|---|---:|---|
| 00 | 目标、工程基线与双平台测量 | 4 | 明确测试设备、预算和复现路线，PC 与移动端各有一份可追溯基线。 |

## 详细任务

### 阶段 00：目标、工程基线与双平台测量

阶段验收：明确测试设备、预算和复现路线，PC 与移动端各有一份可追溯基线。

#### 00.01 确定双平台设备与性能预算

优先级：P0；预计投入：2 次；依赖：无；状态：未开始。

目标：明确实验的共同约束，避免根据开发机表现选方案。

- [ ] 记录 PC 与移动端设备、OS、图形 API、分辨率、可用测试条件；Android/iOS 分别标记实际覆盖情况。
- [ ] 为每档设备填写目标帧率、CPU/GPU 帧耗时、内存上限、流送峰值和最大移动速度；先测量再确认数值。
- [ ] 保存设备与预算表，标明尚未实测的平台和预算调整规则。

产物：设备矩阵、性能预算表。

验收：至少有一台 PC 和一台移动设备作为基线；不可用的平台明确标为未验证，不用 Editor 结果代替。

#### 00.02 记录工程与资源基线

优先级：P0；预计投入：1 次；依赖：00.01；状态：未开始。

目标：固定当前 Unity、URP 与插件环境。

- [ ] 记录 Unity 6000.3.22f1、URP 17.3.0、Amplify Impostors 1.0.2，以及当前 PC/Mobile 画质配置。
- [ ] 确认现有第三方资源的许可和备份方式，建立版本管理方案并排除 Library、Temp、obj 等生成目录。
- [ ] 建立实验记录模板：问题、假设、配置、步骤、数据、结论、来源。

产物：环境清单、实验记录模板、版本管理规则。

验收：能从记录还原实验环境；自有实验与插件原文件的边界清楚。

#### 00.03 建立自动巡游与指标采样

优先级：P0；预计投入：3 次；依赖：00.02；状态：未开始。

目标：让技术方案在同一路线、同一场景密度下比较。

- [ ] 设计固定种子和相机路线，覆盖平原、密林、建筑遮挡、洞口与高速移动。
- [ ] 记录 CPU/GPU 时间、帧时间 P50/P95/P99、长帧次数、GC、批次、三角形、内存与加载事件。
- [ ] 分别执行冷启动和预热后的三次采样，记录构建、图形设置和采样开销。

产物：巡游样例、采样结果、基线报告。

验收：相同配置可重复运行；GPU 指标若平台不可用需注明，不能填推测值。

#### 00.04 完成 PC 与移动端最小构建

优先级：P0；预计投入：2 次；依赖：00.03；状态：未开始。

## 验收与证据规则

- 学习/调研完成：有原始来源、问题与证据等级，能提出可验证实验；不等同实现完成。
- 功能完成：对应样例在 Player 或规定环境验证了正常与异常路径，并保存产物。
- 性能结论：同设备、构建、场景、路线和配置对照，记录重复次数、帧时间与内存；不能只给 FPS 或三角形数量。
- 阶段验收：PC 与至少一个实际移动设备有记录；Android/iOS 未测的一侧明确写未验证。构建、Editor 预览、自动检查与真机视觉分别记载。
- 每个模块记录配置和局限；采用候选方案不是任务的必然结果，证据充分的“不采用”也是有效研究产物。
